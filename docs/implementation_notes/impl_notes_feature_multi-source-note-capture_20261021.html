  1. 2026-10-21

    先定保存規則，再建共同底座

    原本偏重 Siri 語音轉 Notion；擴充後需要知道每筆來源、成果及清理狀態。

    • A｜來源可追溯

      先存來源與固定 ID，再排背景工作；SQLite 保存永久來源與狀態，Redis 負責佇列與短期結果。

    • B–C｜目的地與保存數量

      Drive 成功時文字兩檔、語音三檔、附件一原檔；Notion 留全文與摘要，不上傳附件。主題可停用、用規則或模型分類。

    • D–E｜LINE 與清理

      收件先驗簽及 owner 私聊；校對、明確預覽、確認／取消共用管理服務，垃圾桶操作可重試。

    • F｜可部署、可恢復

      固定加密 key、共用私人 volume、鎖版依賴及內容不進日誌。每階段先獨立審查再提交。

更新部署時要一起做

  • 環境設定變更需重建 web、worker、line-worker；只 restart 不會載入新設定。
  • 三者共用同一 data volume 與固定加密 key；同機 SQLite／flock，不擴展成多主機共用網路磁碟。
  • nginx 動態解析 Docker DNS；Redis 不公開到主機。
  • 單 worker 手動部署仍可消費兩佇列；Compose 的角色分流需使用新版啟動設定。

後續維護與驗收

  • Linode 的 CPU、記憶體、HTTPS 代理與備份恢復要實際驗證。
  • 一般 BYOK、轉送 IP 限流及 multipart 的既有風險，未因本次個別審查全部結案。
  • 固定 key 或私人 volume 遺失，不能靠重試取回加密待處理資料。
  • 新增控制程序改善排隊；CPU 滿載、Drive 網路及大批次完成時間仍需量測。
